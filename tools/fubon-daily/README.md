# 富邦每日行情抓取程式

每個平日 16:45、18:00、19:00 由 Windows 排程 `DayTradeTycoonMarketData` 執行，抓取上市普通股的富邦 1 分 K，寫入 `%USERPROFILE%\YilutekServices\DayTradeTycoon\market-data\`。設計見 `docs/superpowers/specs/2026-10-16-fubon-daily-pipeline-design.md`。

- **只讀行情**：不呼叫帳務或下單 API。
- **登入設定**：`C:\Users\kevin\.fubon\credentials.local.py`，由使用者自己填寫。程式只用 `ast` 讀字串、不執行；設定檔放在 Git 專案裡會被拒絕。
- **排程執行的複本**：排程跑的是 `DayTradeTycoon\fetcher\app\` 裡的複本，不是 repo 的工作目錄。改了程式要先提交，再執行 `install.ps1 -App`。
- **最後一次執行**：18:50 以後開始的執行，視為當天最後一次，失敗時跳出 Windows 通知。

## 逐筆成交（2026-10-20 起）

富邦的逐筆成交（`intraday/trades`）只提供當天，沒有日期參數，所以每天的排程都會順便收下來，錯過就補不回來。

- **抓哪些股票**：當天有成交的全部上市普通股（2026-10-21 起，約 1,050 檔；10/20 只抓教材股與成交值前 20 名）。成交值大的先抓，時間不夠被截斷時，先保住成交最多的股票。
  - 用 10/20 的資料估算：每天約 85–190 萬筆、3,500–5,600 次呼叫、20–40 分鐘、存檔 20–40 MB。
  - 16:45 那次因此會跑 45–65 分鐘。2026-10-21 以前排程設定是「已有工作在跑就不再啟動」，17:30 那次常被 Windows 直接略過（日誌裡不會留下紀錄）。之後改成：
    - 中間那次重試改到 18:00。
    - 還在跑的時候到點的觸發改成排隊，等前一次跑完馬上開始，不再略過。這樣 18:00 那次如果要從頭抓（例如 16:45 登入失敗），跑過 19:00 也不會吃掉最後一次；晚開始的那次仍算最後一次，因為看的是它自己的開始時間（18:50 以後）。
- **順序**：快照之後馬上抓逐筆，接著才抓處置股清單和 1 分 K。逐筆失敗只記在狀態檔，不會擋住 1 分 K 上架。
- **先存再檢查**：富邦的回應一收到就先存進暫存區，再做檢查，所以檢查規則寫錯也不會丟資料。
- **重抓**：遇到下面幾種情況，這一次先不上架，下一次排程再處理：
  - 富邦回 404 或空的：重抓。
  - 抓到一半出錯：已經抓到的頁面留作備份，重抓。
  - 逐筆量少於當日量：這次的回應留作備份，重抓。
  - 沒通過檢查：保留原本的回應，下一次直接拿它重新檢查，不再重抓。
  - 已經抓齊的股票，不會再抓一次。
- **備份**（2026-10-21 起）：不完整的回應不再刪掉，放進暫存區的 `fallback\<代號>\`。
  - 只增不改：同一檔可能有好幾份備份，每一份都留著，寫入時不比較、不覆蓋。
  - 抓到一半中斷的備份一律算不完整，就算張數剛好等於當日量也一樣：中斷之後的成交（例如 14:30 的盤後定價）可能沒抓到。
  - 讀得到但解不開的回應（檔案壞掉）也不刪，移進備份區，這檔重抓。
  - 暫時讀不到的檔案（例如被防毒軟體鎖住）也不刪：前兩次執行這檔算失敗，下次再讀；最後一次會再讀一次，還是讀不到就算失敗，原始檔照樣上架當證據。如果這天沒有其他可以上架的，就整天留給隔天補上架，那時通常讀得到。
- **最後一次執行**：18:50 以後那次，會把手上有的全部上架，並跳出 Windows 通知。
  - 少於當日量的，標成 `"complete": false`，manifest 裡這檔的 `note` 寫原因。
  - 這次沒抓到（富邦出錯、抓到一半中斷，或時間用完），或抓到的比備份少：用一般時段張數最多的那份上架，也標成 `"complete": false`，日誌記一行「…改用留下的備份」。張數一樣多時，沒中斷的優先（中斷之後可能還有盤後定價），再來是盤後張數多的，再來是比較新的。
  - 拿到完整的回應，或拿到沒通過檢查的回應：照舊用那份。沒通過檢查的，原始回應連同原因放進 `rejected`。
  - 沒用來上架的回應，全部一起放進上架資料夾的 `fallback\<代號>\`，不會刪掉。
- **補上架**：前一天的逐筆（包括備份）如果還留在暫存區（例如晚上的排程沒跑到），之後任何一次執行都會先把它上架，不需要登入，規則和最後一次執行一樣。
  - 某一檔出錯不會擋住其他檔；沒有全部抓齊時會跳出通知，因為那天的最後一次沒有跑到。
  - 只剩解不開的回應的日子也會上架（只有證據、沒有成交），不會一直留在暫存區、每次都通知。只有補上架會這樣做，平常的執行不會。只要有一檔是「這次讀不到、下次可能讀得到」，就不這樣做，等下一次再試（沒抓齊時每次都會通知）。
  - 讀不到暫存區時，這次先不補上架，當天的抓取照常進行。
- **時間上限**：前兩次執行，逐筆超過 45 分鐘就不再開始抓新的股票，留時間給 1 分 K。排程跑滿兩小時會被 Windows 停掉，所以最後一次也有上限，要留時間給上架和通知：
  - 還要補抓 1 分 K 時，逐筆最多 70 分鐘。
  - 1 分 K 已經上架、只剩逐筆時，最多 100 分鐘。
  - 上限只在兩檔之間檢查。卡在某一次呼叫裡的情況，由每次呼叫的逾時處理（見下面「富邦呼叫的逾時」）。
- **富邦連續出錯**：前兩次執行如果連續 15 檔重試後仍然出錯，就當作富邦暫時故障，這次不再開始抓新的股票，留給下一次；已經抓到的照常檢查。最後一次沒有下一次了，所以不受這條限制，只受時間上限。停下來的原因會寫在狀態和通知的最前面。
- **存放位置**：`market-data\ticks\<日期>\`。
  - `manifest.json`：股票清單、筆數、`rejected`、警告，以及每個檔案的雜湊。不完整的股票有 `note`（原因）。
  - `symbols\<代號>.json.gz`：每筆 `[09:00 後的毫秒, 成交價, 單量(張), 買價, 賣價]`。
  - `raw\<代號>.json.gz`：這檔最後留下的富邦原始回應；這檔在 `symbols` 或 `rejected` 裡時，就是它們用的那一份。
  - `fallback\<代號>\<編號>.json.gz` 和 `<編號>.json`：沒拿來上架的其他回應（富邦原始回應），以及當時的快照資料和中斷原因。只有發生過才會有。
- **保留期限**：永久保留，不會被清理。
- **盤後定價**：14:30 的盤後定價成交也會出現在逐筆裡。2026-10-20 實測：這筆沒有累計量、沒有買賣價，流水號是 99999999，而且快照的當日量不含它。所以 13:35 以後的成交另外存在 `afterHours`，manifest 記下它的筆數和張數，不列入當日量比對。
- **檢查**（只看一般交易時段，也就是 13:35 以前，延後收盤也算在內）：
  - 時間必須在當天 09:00–14:30 之間。13:35–14:00 之間如果有成交，記成警告。
  - 流水號要遞增，累計量必須等於逐筆單量加總。
  - 一般時段的逐筆總量少於當日量時，判為不完整，要重抓。總量多於當日量，或最後成交價和快照收盤價不同時，記成警告。
- **實測的富邦格式**（2026-10-20）：
  - 每頁最多 500 筆，`limit` 設多大都一樣；抓到最後一頁之後會回空的頁面。
  - 時間是微秒，單量以張計算。台積電一天約 4,600 筆、11 次呼叫，原始資料約 530 KB。
- **狀態**：結果寫在 `status.json` 的 `ticks` 欄位。講師卡片目前還不顯示。
- **補抓**：用 `--date` 補抓過去的日子時，只抓 1 分 K，不抓逐筆。

## 富邦呼叫的逾時（2026-10-21 起）

富邦 SDK 的行情呼叫（快照、處置股清單、逐筆、1 分 K）本身沒有逾時：最後都是 SDK 內建的 `fugle_marketdata` 在 `rest/base_rest.py` 用 `requests.get` 送出，沒有 timeout，也沒有設定可以加。伺服器連上後不再回應時，整次執行會卡到排程跑滿兩小時、被 Windows 停掉，不上架也不通知。

- **做法**：登入後，只把那個模組裡的 `requests` 換成替身（`fubon_daily/client.py` 的 `TimedRequests`），每次 GET 加上 `timeout=(10, 60)`：連線最多等 10 秒，之後每次讀取最多等 60 秒。其他東西（包括 `requests.exceptions`）都是原本的套件，SDK 自己的錯誤處理不變。不改 SDK 的檔案，也不用執行緒。
- **只換檢查過的版本**：`fugle_marketdata` 要是 2.7.0rc1（`fubon_neo` 2.4.0 指定的版本），而且那個模組裡的 `requests` 就是 requests 套件本身，才會換。別的版本可能改用別的方式送出，替身管不到，所以不換。
- **逾時之後**：當成一般的富邦錯誤，照原本的規則。同一個呼叫最多試 3 次，還是失敗的話：
  - 逐筆：這檔算沒抓到，已抓到的頁面放進備份。前兩次執行留給下一次重抓，最後一次用留下的最完整的回應上架（標成不完整）。
  - 快照、處置股清單、1 分 K：這次執行記「抓取中斷」，下一次排程再抓。
  - 每試一次最多約 80 秒（連線 10 秒、加密連線的握手 10 秒、讀取 60 秒）。所以富邦的行情伺服器整個不回應時，每次執行也會在兩小時內結束。
- **日誌**：每次執行「登入成功」那一行會寫「富邦行情呼叫逾時：連線 10 秒、每次讀取 60 秒」。沒有換的時候（SDK 版本不同、送出方式不同或找不到那個模組），照舊執行，那一行改寫「富邦行情呼叫沒有逾時：（原因）」。
- **重裝或升級 SDK 之後**（`install.ps1 -Sdk`）：用排程的 Python 跑一次測試（見下面「測試」）。版本不是 2.7.0rc1 時不會加逾時，測試也會失敗；要先讀過新版的 `fugle_marketdata/rest/base_rest.py`，確認還是用 `requests.get` 送出，再改 `client.py` 的 `CHECKED_FUGLE`。
- **沒有涵蓋**：
  - 登入、`init_realtime`、登出在編譯過的元件裡，沒有逾時參數，仍然只有排程的兩小時上限。
  - 查網址（DNS）不算在逾時裡，交給 Windows。
  - 一直有資料進來的回應（每段間隔不到 60 秒）不會被截斷，所以傳得慢的大回應不會被誤判，但一點一點拖著不送完的伺服器也擋不住。
  - 只有部分呼叫卡住、重試又成功時，每卡住一次多花約一分鐘。1 分 K 沒有時間上限，卡住的次數一多，整次執行仍可能跑滿兩小時被停掉：不上架 1 分 K、不通知；如果是當天最後一次，那天的 1 分 K 要用 `--date` 手動補抓。逐筆在 1 分 K 之前就已經存進暫存區（最後一次會先上架），不受影響。
- 細節見 `docs/fubon-ticks-full-market-2026-10-21.md` 的「富邦行情呼叫加上逾時」。

## 測試（不需要登入，也不會連到富邦）

```powershell
py -3.12 -m unittest discover -s tools/fubon-daily/tests -t tools/fubon-daily -v
```

`tests/test_never_lose.py` 用假富邦跑 25 個隨機情境（每天三次，每檔每次隨機給完整、量不足、中斷、最後一頁中斷、沒通過檢查、出錯或查無；約三分之一的情境 19:00 沒跑，由隔天補上架），檢查富邦給過的每一份逐筆回應都剛好上架一次，而且每檔的成交都來自張數最多的那份。

`tests/test_client.py` 的 `InstalledSdkTest`（4 個）要用真的 SDK 程式，對本機的假伺服器測逾時，所以只在排程用的 Python 跑；用上面的 `py -3.12` 會跳過：

```powershell
& "$env:USERPROFILE\YilutekServices\DayTradeTycoon\fetcher\.venv\Scripts\python.exe" -m unittest discover -s tools/fubon-daily/tests -t tools/fubon-daily -v
```

## 安裝與更新

```powershell
powershell -NoProfile -File tools\fubon-daily\install.ps1 -Sdk    # 建立 Python 3.12 環境並安裝官方 SDK 2.4.0（雜湊記錄在 fetcher\sdk-lock.json）
powershell -NoProfile -File tools\fubon-daily\install.ps1 -App    # 複製已提交的程式
powershell -NoProfile -File tools\fubon-daily\install.ps1 -Task   # 建立／更新排程
```

## 手動執行

```powershell
$fetcher = "$env:USERPROFILE\YilutekServices\DayTradeTycoon\fetcher"
& "$fetcher\.venv\Scripts\python.exe" -X utf8 "$fetcher\app\fetch_daily.py" --data "$env:USERPROFILE\YilutekServices\DayTradeTycoon\market-data" --credentials "$env:USERPROFILE\.fubon\credentials.local.py"
# 補抓過去的日子（可只抓部分股票）：
#   ... --date 2026-10-05 --symbols 2330,2317,2454,2382,2308
```

結束碼：0 表示成功、休市或已完成；1 表示失敗，等下一次排程；2 表示設定、登入、憑證或 SDK 錯誤，需要人處理。狀態在 `market-data\status.json`，每日日誌在 `market-data\logs\`。
